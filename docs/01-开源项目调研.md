# 开源项目调研 · 2026-11

> 目的：动手前先看别人踩过哪些坑，避免重复造轮子，也避免踩到别人的雷（尤其是许可证）。
> 结论会反向修改 `00-产品与技术框架.md`，改动清单见第 7 节。

## 0. 一句话结论

**没有一个开源项目在做「我们想要的东西」的完整版**——大多偏"发布调度"或"单平台爬虫"。但有 3 个项目的设计细节值得直接搬，其中 1 个（MediaCrawler）**代码不能用，只能学思路**，因为它的许可证禁止商用。

## 1. 三个必须调整的判断

### 1.1 「自己的数据」应该从创作者后台拿，不是公开页面

这是我之前方案里的一个错误。我原本打算用插件抓公开页面（播放、点赞、评论），但漏了一件事：

**完播率、3 秒留存、涨粉来源、粉丝画像，这些只有创作者后台有，公开页面永远不显示。**

而这两个恰恰是判断"视频为什么不火"最核心的指标。抓公开页面等于放弃了最有价值的那一半数据。

正确做法是拆成两个采集目标：

| 采集目标 | 去哪 | 拿到什么 | 手段 |
|---|---|---|---|
| **我的作品** | 创作者后台（creator.douyin.com / creator.xiaohongshu.com） | 完播率、留存曲线、涨粉、粉丝画像 | 浏览器自动化，复用本人登录态 |
| **别人的爆款** | 公开页面（搜索页 / 作者主页 / 话题页） | 播放、赞、评、藏、时长、标题 | 关键词搜索 + 主页遍历 |

两套管道，两套频率，互不干扰。这个区分是从 [`Xavier-168/data-scientist-community`](https://github.com/Xavier-168/data-scientist-community) 学到的——它专门连的是"创作者后台"，不是公开页。

### 1.2 「实时」要改成「可信的实时」

几乎每个自建数据看板都会犯同一个错：**采集失败了，但页面上还显示着昨天的数据，看起来像刚更新的。**

[`bzwh321/self-media-data-console-bzwh`](https://github.com/bzwh321/self-media-data-console-bzwh) 的做法值得抄：刷新流程必须依次通过「规范化 → 业务契约校验 → T-1 新鲜度检查」才更新看板，任一步失败就显示失败原因，**绝不把缓存数据标成"刷新成功"**。

对我们更实际的是这三个机制：

1. **数据契约**：每个平台的每个指标要有明确定义和合理区间，比如完播率必须在 0–100%，涨粉数不能是字符串。校验不过就拒绝入库，而不是存进去以后算出一堆怪结论。
2. **新鲜度标记**：每个账号卡片显示"数据截至 X 分钟前"，超过阈值变黄、再超变红。
3. **失败可见**：采集失败要在总览页有个告警，而不是悄悄空着。

> 这条比任何功能都重要。**数据看板一旦开始骗人，你就不会再信它了。**

### 1.3 私信代发：dry-run + 台账，是这类工具的共识

[`hanliang97/MatrixMedia`](https://github.com/hanliang97/MatrixMedia) 做评论回复时用了一个设计：`cli comments-reply` **默认 dry-run（只打印不发）**，必须加 `--execute` 才真发，且全程记台账。

这和我们的私信设计完全一致，说明这不是过度谨慎，是这类工具的默认姿势。可以再加一层：dry-run 时把"将要发出的内容"显示在气泡里给你确认，而不是终端里一行字。

## 3. 逐个项目要点

### 3.1 MediaCrawler（70k）— 只学思路，别碰代码

国内最出名的多平台采集器，支持小红书、抖音、快手、B 站、微博、贴吧、知乎，功能覆盖：关键词搜索、指定帖子、二级评论、指定创作者主页、登录态缓存、评论词云。

**核心做法**：不逆向 JS 签名，而是用 Playwright 保存登录态，在浏览器上下文里直接执行 JS 表达式拿签名参数。

⚠️ **许可证是 `NON-COMMERCIAL LEARNING LICENSE 1.1`，明确禁止商用。** 它的 README 里甚至挂了"爬虫违法违规案件"的链接。

**能拿走的**：
- 「关键词搜索 + 指定创作者主页」正好是爆款雷达需要的能力
- 「登录态缓存 + 浏览器上下文执行 JS」避免逆签名，维护成本低得多
- 评论二级抓取（评论的回复），做口碑监控要用

**不能拿的**：任何代码。思路可以自己实现。

### 3.2 MatrixMedia（1.2k）— 采集层最佳参考

Electron 做的多平台矩阵发布工具，支持抖音、快手、小红书、B 站、视频号、百家号、头条、番茄视频。

**最有价值的是它的「三级取数策略」**（原帖写在掘金）：
```
页面上下文 fetch  →  被动嗅探（拦 XHR）  →  主进程直取
        失败降级         失败降级
```
三种手段逐级兜底。这比我们原方案"只拦 XHR + DOM 兜底"更完整——**页面 fetch 是最轻的，什么都不用解析，但有签名限制；嗅探最稳；直取是最后手段。**

其他值得抄的：
- **单并发 + 限速**，明确不绕风控
- **session partition 共享**：GUI 和 CLI 用同一个 `persist:` 分区，登录一次两边都能用
- **CLI / HTTP API / MCP 三路通道**：`POST 127.0.0.1:30088/publish`，任何程序都能触发
- **退出码约定**：0 成功 / 1 异常 / 2 参数错误 / 3 业务失败

> 第三点对我们有启发：现在只做 Web 界面，但**留一个 CLI 的坑位**几乎零成本，以后想让 AI agent 自动查数据、自动复盘，就不用重构。

### 3.3 数据科学家 Community（35）— 本地优先的示范

一位抖音博主开源的个人工具，macOS，连抖音/小红书/B站/快手的**创作者后台**，做字段归一化，导 Excel，可选同步飞书。

值得抄的细节：
- **登录态存在 `~/Library/Application Support/...`，不写进源码目录**，也不上传
- **登录态检查有 `unknown` 状态**：网络抖动、503、空白页时记为 unknown，保留上次的 authorized，**不因为一次探测失败就要求重新扫码**
- **明确承认平台会变**："平台页面和接口可能随时变化，采集适配不保证持续可用"
- **不做 Cookie 自动刷新**，只做状态检查，不承诺登录态永不过期

最后两条是一种诚实的态度，比"保证 7×24 稳定"的承诺更可信。

### 3.4 自媒体数据中控台（2）— 契约校验的范本

Windows 本地，Python，支持小红书/抖音/知乎/B站/公众号。**数据来源不是爬虫，而是从官方创作者后台手动导出 Excel/CSV**，再交给 AI 整理入库。

这个思路很务实：官方后台本来就提供导出功能，导出的是准确数据，零风控风险，只是要手动点一下。

它的工程细节值得抄：
- `data/demo/` 与 `data/user/` **物理隔离**，演示数据永远不会混进真实数据
- **业务契约校验**：字段缺失、区间越界直接报错，**"没有静默补零"**
- **T-1 新鲜度检查**：个人模式要求数据不超过 T-1
- 刷新失败显示原因，**不把缓存说成刷新成功**

而且是 **MIT 许可证**，是这几个里唯一可以放心参考代码的。

### 3.5 Postiz（41k）— 产品形态参考，架构太重

Next.js + NestJS + Prisma + PostgreSQL + Temporal 的 monorepo。功能是"排期发布 + 分析 + 团队协作"，覆盖 20+ 平台。

**它验证了一个关键事实**：自建版必须"自己去每个平台建开发者应用并走审核"，文档原话——Meta、YouTube、TikTok 的审核**要几周**。这坐实了我们不走官方 API 主路径的判断。

**不抄的**：Temporal（工作流引擎，我们一个 node-cron 就够）、NestJS 微服务拆分（一个人用不着）、PostgreSQL 强依赖（本地 SQLite 更省事）。

### 3.6 Chatwoot（39k）— 收件箱数据模型范本

开源客服系统，核心是 MIT。它的 `conversation / message / contact / canned response / assignment` 模型是业界验证过的，我们收件箱基本可以直接对齐这套概念，尤其是：

- **canned response（预设话术）**：我们叫"话术库"
- **conversation status**：open / pending / resolved —— 比我们原来的 `is_replied` 布尔值合理得多（真实场景里会话会反复）
- **contact 独立建模**：同一个人可能在小红书和闲鱼都找你，可以合并

### 3.7 ai-goofish（0）— 闲鱼确实能采

Playwright + FastAPI 的闲鱼商品监控，支持关键词、价格区间、个人闲置筛选，采商品信息和卖家资料。

结论：**闲鱼用 Playwright 驱动登录态是可做的**，和另外两个平台同一套技术栈，不需要单独方案。

## 4. 可以直接抄的 8 个设计

| # | 设计 | 来源 | 成本 |
|---|---|---|---|

| 2 | 数据契约校验（区间 + 必填），不过不入库 | 数据中控台 | 低 |
| 3 | 新鲜度标记 + T-1 检查 | 数据中控台 | 低 |
| 4 | demo 数据与真实数据物理隔离 | 数据中控台 | 极低 |
| 5 | 登录态存用户目录，不进仓库 | 数据科学家 | 极低 |
| 6 | 登录态检查的 `unknown` 状态（不误判） | 数据科学家 | 低 |
| 7 | 干跑（dry-run）+ 台账（audit log） | MatrixMedia | 低 |
| 8 | 会话状态用 open/pending/resolved，不是布尔 | Chatwoot | 极低 |

## 5. 明确不做的 5 件事

| 不做 | 原因 |
|---|---|
| 自建代理池 / 多账号轮换 | 我们是"用自己账号看自己数据"，不需要；而且这是平台最敏感的行为 |
| 逆向 JS 签名 | 平台一更新就废，维护成本无底洞 |
| Electron 桌面壳 | 你要的是 web；本地跑 `pnpm dev` 已经够 |
| Temporal / 微服务 | 一个人用，node-cron 足够 |
| 自动关注、自动点赞、自动评论 | 这不是产品目标是刷量工具，风险极高 |

## 6. 许可证风险（重要）

| 项目 | 能否参考代码 | 边界 |
|---|---|---|
| **MediaCrawler** | ❌ | 非商用许可证，只能学思路，一个字都不能抄 |
| Postiz | ⚠️ | AGPL-3.0：改了并且对外提供服务，必须开源 |
| MatrixMedia | ⚠️ | GPL-2.0：同上 |
| 数据科学家 | ⚠️ | AGPL-3.0：同上 |
| 自媒体数据中控台 | ✅ | MIT，可以放心参考 |
| Chatwoot 核心 | ✅ | MIT，可以放心参考 |

**结论**：我们自己从零写，只在思路上借鉴。这样既没有许可证负担，代码也更贴合你的场景（别人的通用产品反而更重）。

如果哪天要开源我们自己的项目，MIT 是最省事的选法。

## 7. 对框架的具体修改

| 改动 | 原方案 | 新方案 | 影响 |
|---|---|---|---|
| 采集目标拆分 | 插件抓公开页 | 自己的数据走**创作者后台**，别人的爆款走**公开页** | 数据完整性大幅提升，工作量 +2 天 |
| 采集降级 | 拦 XHR + DOM 兜底 | 三级降级：页面 fetch → 嗅探 → 直取 | 稳定性提升 |
| 数据校验 | 无 | 契约校验 + 新鲜度 + 失败可见 | +1 天，但值得 |
| 会话状态 | `is_replied` 布尔 | open / pending / resolved | 模型更贴合真实场景 |
| 增加 CLI 通道 | 无 | 预留 `pnpm cli` 入口 | 零成本，为 AI 自动化铺路 |
