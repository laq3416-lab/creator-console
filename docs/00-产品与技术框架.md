## 1. 一句话定位

一个**只给我自己看**的多平台内容作战台：把抖音、小红书、闲鱼的账号数据、作品表现、评论私信收进一块屏，用「规则预警 + 大模型复盘」告诉我**下一条该发什么、这条为什么不行**。

## 2. 已锁定的决策

| 维度 | 决策 | 说明 |
|---|---|---|
| 平台 | 抖音、小红书、闲鱼 | 前两个是内容平台，闲鱼同时是内容 + 客服 |
| 采集 | 双管道：创作者后台（自己）+ 公开页（对标） | 浏览器自动化复用本人登录态；官方 API 不作为主路径（个人拿不到权限） |
| 用户 | 先 1 人（3–5 账号），预留团队 | 所有表带 `workspace_id`，先写死默认值 |
| 部署 | 先本地 → 局域网（手机可看）→ 云 | 三步走，前两步代码零改动 |
| 建议引擎 | 规则引擎 + 大模型 | 规则管实时预警，模型管深度复盘 |
| 私信 | 只看不回 + 可选代为发送 | 自动发送默认关闭，需逐条确认 |
| 大模型 | DeepSeek 为主，其他家留适配 | 统一 `LLMProvider` 接口 |
| 技术栈 | Next.js 15 + TS + Drizzle + SQLite | 见第 6 节，本地零依赖启动 |

## 3. 功能分层（MVP → V1 → V2）

### MVP（先跑通，约 1–1.5 周）
- 账号矩阵卡片：粉丝数、今日涨跌、近 7 日趋势
- 作品库：列表 + 筛选 + 排序，单个作品的播放/点赞/评论/收藏曲线
- 统一收件箱：评论 + 私信按平台聚合，未读标记、星标
- 规则预警：5 条硬规则，命中即在总览页出卡片
- 采集：Chrome 插件跑通抖音一个平台

### V1（可用，再 1–2 周）
- 小红书、闲鱼接入（闲鱼含商品维度 + 咨询收件箱）
- LLM 复盘：单作品诊断、周报、选题建议
- 评论情感分析 + 高频问题提取（自动出「话术库」）
- 发布时间热力图、爆款因子对比

### V2（按需）
- 私信代为发送（人工确认 → 自动填表发送）
- 团队多账号、角色权限、账号分配
- 云端部署 + 手机端 PWA
- 自动生成图文/脚本草稿

### 4.1 可点原型

已经做了一个单文件可点原型，先看长相再决定要不要改结构：

- 文件：`prototype/index.html`（双击用浏览器打开即可，无需安装任何东西）
- 覆盖：总览 / 账号矩阵 / 作品库 / 收件箱 / 智能建议 五个页面
- 三套主题右上角直接切，选择会记住
- 支持跳转参数：`?theme=light&view=inbox`（方便直接打开某一页）

> 原型里的数据全部是示意数据，用来确认**信息密度和层级**，不是真实指标。

**总览页信息优先级**（从上到下）：
1. 今天必须处理的事：未读私信、待回复评论、失败采集
2. 三个平台的核心数字 + 涨跌
3. 预警卡片（红/黄）
4. 近 7 日作品表现排行

## 5. 数据模型

### 5.1 实体关系

```
workspace ─┬─ account ──┬─ content ──┬─ comment
           │             │            └─ metric_point
           │             └─ conversation ── message
           ├─ suggestion
           ├─ rule
           └─ sync_job
```

### 5.2 核心表

**workspace** — 当前只有 1 行，团队版的隔离单位
`id, name, plan, created_at`

**account** — 一个平台的一个账号
`id, workspace_id, platform(douyin|xhs|xianyu), handle, nickname, avatar_url, follower_count, status, credential_ref, last_synced_at`

> `credential_ref` 只存「本地加密存储的引用」，登录态绝不明文入库、绝不上传服务器。

**content** — 作品 / 笔记 / 商品，三平台共用一个模型
`id, account_id, platform_content_id, type(video|note|item), title, cover_url, url, published_at, tags, raw_json`

**metric_point** — 通用指标点（关键设计）
`id, entity_type(account|content), entity_id, key, value, captured_at`

> 用 **key-value 长表**而不是给每个平台建宽表，理由：抖音有完播率、小红书有收藏/涨粉、闲鱼有想要/成交，指标集完全不同。长表加指标零成本，配一层「指标字典」做展示层映射。

**comment**
`id, content_id, platform_comment_id, author, text, like_count, sentiment, is_replied, created_at`

**conversation / message**
`conversation: id, account_id, peer_name, peer_avatar, unread_count, last_message_at, tags, status(open|pending|resolved)`
`message: id, conversation_id, direction(in|out), text, attachments, created_at, is_read`

**suggestion** — 系统的产出物
`id, workspace_id, scope(account|content), target_id, source(rule|llm), rule_id, severity(red|yellow|info), title, rationale, action, status(new|read|done|ignored), created_at`

**rule** — 可配置的阈值
`id, platform, metric_key, operator, threshold, window_hours, severity, enabled`

**sync_job** — 每次采集的审计
`id, source(api|plugin|manual), platform, status, items_count, error, started_at, finished_at`

## 6. 技术栈与工程结构

### 6.1 选型理由

| 层 | 选择 | 为什么 |
|---|---|---|
| 框架 | Next.js 15 (App Router) | 前后端一体，本地 `pnpm dev` 就能跑 |
| 语言 | TypeScript | 指标计算和数据结构多，类型能省大量调试 |
| 数据库 | SQLite (libsql) → 可切 Postgres | 本地零安装；表设计一致，换库只改连接串 |
| ORM | Drizzle | SQL 友好，迁移文件可读，别用黑盒 |
| UI | Tailwind + shadcn/ui | 数据密集型界面，组件可控 |
| 图表 | Recharts | 曲线/柱状够用，SSR 友好 |
| 采集 | Chrome MV3 扩展 | 用你自己的登录态，不碰密码 |
| 任务 | node-cron（本地 worker） | 采集、计算、触发建议 |
| 模型 | DeepSeek（可换） | 统一 Provider 接口 |

│  │  └─ src/app/(dashboard)/...

### 6.3 采集链路（两条管道）

调研后修正：**自己的数据和别人的数据来源不同、频率不同，必须拆成两条管道。**

**管道 A：我自己的作品 → 创作者后台**

```
创作者后台（creator.douyin.com / creator.xiaohongshu.com）
   ↓  浏览器自动化，复用本人登录态（不碰密码）
三级取数：页面上下文 fetch → 被动嗅探 XHR → 主进程直取（逐级降级兜底）
   ↓
归一化 → 契约校验 → 写入 metric_point
```

为什么必须回后台：**完播率、3 秒留存、涨粉来源、粉丝画像，公开页面永远不显示**。这几个恰恰是判断"为什么不火"的核心，只抓公开页等于放弃了最有价值的一半。

**管道 B：别人的爆款 → 公开页面**

```
关键词搜索页 / 作者主页 / 话题页
   ↓  低频遍历（每日一次，单并发 + 限速）
公开指标：播放、赞、评、藏、时长、标题、发布时间
   ↓
归一化 → 爆款指数计算 → 写入 benchmark_content
```

**三级取数降级**（参考 MatrixMedia）：

| 级别 | 手段 | 优点 | 失败时 |
|---|---|---|---|
| 1 | 页面上下文 fetch | 最轻，不用解析 DOM | ↓ |
| 2 | 被动嗅探 XHR | 最稳，拿到的就是接口原始 JSON | ↓ |
| 3 | 主进程直取 | 兜底，能拿到深链数据 | 报失败，不静默 |

**为什么优先拦 XHR 而不是解析 DOM**：页面结构一改 DOM 就废，接口返回的 JSON 稳定得多。DOM 只做最后一层兜底。

**采集频率**：自己账号 15 分钟一次；对标爆款每日 03:00 一次。绝不做高频轮询，单并发 + 限速，不逆向签名。

### 6.4 数据可信度（比功能更重要）

几乎所有自建看板都会死在同一个地方：**采集失败了，页面还显示昨天的数字，看起来像刚更新的。** 数据看板一旦开始骗人，你就不会再信它了。

三道闸门，缺一不可：

1. **契约校验**：每个指标有定义和合理区间（完播率 0–100%、涨粉不能是负数、播放量不能为字符串）。校验不过**拒绝入库**，绝不静默补零。
2. **新鲜度标记**：账号卡片显示"数据截至 X 分钟前"，超阈值变黄、再超变红，不是只显示绿色小圆点。
3. **失败可见**：采集失败要在总览页出一条告警，而不是悄悄空着。

另外 `data/demo/` 与 `data/user/` 物理隔离——演示数据永远不会混进真实数据。

### 6.5 规则引擎（MVP 的 5 条）

| 规则 | 条件 | 产出 |
|---|---|---|
| 完播率偏低 | 视频完播率 < 30% 且播放 > 1000 | 「前 3 秒没留住人，试换开头钩子」 |
| 互动率异常 | 点赞率 < 2% 且播放 > 5000 | 「内容对味但没激发动作，结尾加引导」 |
| 涨粉突然加速 | 24h 涨粉 > 均值 3 倍 | 「有爆款苗头，立刻追同题材」 |
| 评论情感转负 | 近 20 条负面占比 > 40% | 「出现口碑风险，优先回复」 |
| 私信堆积 | 未读 > 10 条且超 2 小时 | 「有咨询要接，流失就是丢单」 |

阈值全部进 `rule` 表，不写死在代码里。

### 6.6 LLM 建议的输入输出

**输入**：作品近 7 天指标序列 + 该账号历史中位数 + 同类型作品 Top3 对比 + 评论摘要（不是原始评论，省 token）

**输出（强制 JSON）**：
```json
{
  "diagnosis": "这条的问题在开头 3 秒",
  "evidence": ["完播率 22%，账号中位 41%", "前 3 秒跳出 68%"],
  "actions": ["改开头：直接抛结果", "标题去掉形容词"],
  "next_topics": ["同题材反向视角"],
  "confidence": 0.7
}
```

统一 `LLMProvider` 接口，DeepSeek / OpenAI / 其他家只需实现一个 `chat()`。

| 阶段 | 做法 | 你得到什么 |
|---|---|---|
| ① 本地 | `pnpm dev`，SQLite 文件 | 只有你这台 Mac 能开 |

## 8. 风险与红线

| 风险 | 应对 |
|---|---|
| 抖音/小红书官方 API 个人拿不到（需企业资质，私信接口基本不开） | 插件为主路径，API 只当加速项，不当依赖 |
| 闲鱼无开放接口 | 只能插件，且只读商品/咨询，不碰交易动作 |
| 插件采集触发风控 | 低频、随机间隔、只读不写、绝不模拟点击刷量 |
| 登录态泄露 | 存在浏览器本地 + 本地加密，服务端不存 cookie |
| 私信自动发送误发 | 默认关闭；开启后也必须「人工确认 → 再发」 |
| 指标口径混乱 | 建指标字典，每个 key 只有一个定义和一个来源 |
| **数据看板骗人**（采集失败仍显示旧数据） | 契约校验 + 新鲜度标记 + 失败可见，三道闸门 |
| 创作者后台改版导致采集失效 | 三级取数逐级降级；每次失败记 sync_job，连续失败在总览告警 |

## 10. 已定稿与剩余开放项

### 已定稿

| 项 | 结论 |
|---|---|
| 平台 | 抖音、小红书、闲鱼 |
| 首发平台 | **抖音**（数据最有价值，插件最容易验证） |
| 视觉 | **三套主题可切换**：深色数据台 / 浅色清爽 / 亮色高密度 |
| 账号规模 | 现在小（3–5 个），但**按能扛大体量设计**（见 10.2） |
| 私信 | 只看不回 + 可选代发（默认关闭，逐条确认） |
| 模型 | DeepSeek 为主，其他家留 Provider 接口 |

### 10.1 视觉：三套主题

原型里已实现，切换即时生效，图表配色跟着变（浅色主题下青色必须压深，否则白底看不清）。

| 主题 | 适用场景 |
|---|---|
| 深色数据台 | 晚上看数据、盯大屏、长时间不刺眼 |
| 浅色清爽 | 白天办公、看内容截图最真实 |
| 亮色高密度 | 习惯看表格、想要一屏塞下更多行 |

### 10.2 现在账号少，但按大体量设计

不做过度设计，但四个地方现在就写对，以后不用返工：

| 潜在瓶颈 | 现在就要做的 | 成本 |
|---|---|---|
| 作品列表变慢 | 列表**服务端分页**，默认 20 条，不做全量加载 | 一样的工作量 |
| 指标点爆炸（1000 作品 × 90 天 × 8 指标） | 原始点存 `metric_point`，另建**日聚合表**供图表用；查询走聚合表 | 一张表 + 一个定时任务 |
| 总览页每次全表扫 | 总览只读**缓存快照**（每 5 分钟算一次），不实时聚合 | 一个缓存表 |
| 换库/多租户 | 所有表带 `workspace_id`；查询统一走一层 repository | 写代码时顺手 |

> 真正的分水岭是「作品数过万 + 指标点过千万」。到那时 SQLite 换 Postgres、加索引即可，表结构不用动。

### 10.3 还需你确认（不阻塞开工）

1. **每个平台的账号名**：做真实采集时要用，现在可以先用假数据。
2. **DeepSeek Key**：什么时候给我，我就把 LLM 复盘接上；不给就先跑规则。
3. **发布频率**：你大概几天发一条？这决定「涨粉异常」规则的判定窗口。

## 附：为什么不用「每个平台一张表」

看起来更直观，但三平台指标集完全不同，会变成三套页面、三套图表、三套规则。
统一 `content + metric_point` 后：加一个平台 = 加一个 connector + 一张指标映射表，前端零改动。
这是这套框架能在 1 周出 MVP、以后还能加快手/视频号的根本原因。
